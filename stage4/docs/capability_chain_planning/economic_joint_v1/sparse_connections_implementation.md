# 可复用稀疏道路连接与预取—搜索协同

日期：2026-10-17。代码及有界静态准备完成；**没有重新运行仿真**。经济参数和C能力规则保持不变，没有新增C奖励。

## 1. 本轮修正了什么

此前预取独立挑邻近任务，种子和搜索却遍历另一批根状态。另有一处具体错位：预取可能处理即时方案已经接走的真实请求，之后这些请求又会被共享客户容量约束排除。

现在的流程是：

```text
同一历史候选目录 → 有界预取/已有道路证据 → 支持边邻接索引 → 种子与链搜索
```

1. 预取移到本次预测场景对象建立之后，使用搜索本身的时间、空间、能力和收益排序逻辑；跳过即时方案已经占用的请求，不再只跳过本车请求。
2. 预取一条连接成功后，沿同一TopK后继继续准备，按真实道路时间推进，最多三单。仍最多检查64个候选连接、四个可用根/车型；同优先级、同就绪时间的根按轮次轮转，避免永远固定前四辆。所有在线查询共享原预算。
3. 已有道路支持的根优先进入种子恢复；搜索使用同一邻接目录，未准备的根不会再反复进入重型连接器查缓存缺项。
4. 精确调位重算优先准备已认证的调位根，C/HV规则相同。乐观调位提示仍不能执行，未认证道路不能冒充可用道路。
5. 局部搜索优先处理有准备支持的机会，当前服务数、结转服务数、共享客户和共同首动作约束不变。这是搜索组织改进，不是声称有限时限下派单结果逐位等价。

## 2. 候选、证据和未知分开

- **候选目录**只表示既定空间/时间域中的候选，不是道路可通证明。
- **已支持**包含核验取得的原始道路时间、距离和证据类型。C仍须通过其方向、路口和接缝规则；HV证据不冒充C证据。
- **已拒绝**只描述当前有界候选路径及规则下的结果，不证明所有可能道路都不可通。
- **未评估/预算延后**不写成永久拒绝，也不当成物理不可达。它们不再触发搜索中的重复路由证据检查。

持久化只保存正的历史订单→历史订单标量证据，不保存完整Valhalla JSON、不保存真实车辆的临时方向证书。缓存绑定冻结路网、控制/能力规则和有向身份输入；不绑定车费。使用时重新乘实际预测出发时段的时间倍率，再检查接驾和时间窗。

真实车辆方向的紧凑索引每次决策重建，包括同一时刻重入；不会因为车辆ID、时间和位置碰巧相同而沿用旧的进入方向。

该批消耗88/96个查询槽（64次初始评估、24次替代路径请求）；另记录56次标量route调用、77次edge-walk调用、32次HV矩阵评估。这些指标单位不同，不能直接相加当成同一查询量。

道路准备函数记录8.72秒、进程峰值496.75 MiB；该阶段计时不包含解释器启动及函数头部模块导入，不能直接与上一轮包含冷初始化的172.73秒仿真耗时比较。详见[历史道路准备记录](historical_road_preparation.json)。

所有准备只使用既有历史订单、冻结M3输出与冻结路网；没有读取Test31未发生的需求，没有改客户原路线，没有重新训练或跑Stage0—3。

## 4. 开销与限制

在线预算仍是：2个额外查询槽/30秒、32个/5分钟、0.15秒可选连接工作、10秒适配器期限和每轮最多3个局部整数修复块。离线准备是一次单独的32对、最多96槽、180秒批次，**不是把在线预算放大到96**。

只保留单进程和稀疏表；索引按8 MiB估计容量及8192条记录封顶，SQLite按32 MiB/8192条封顶，单个候选目录/根引用受20,000上限约束。总进程仍受1536 MiB限制，不构建车辆×订单×时间稠密矩阵，不使用GPU。

构造的83根状态案例中，搜索结果与同一证据下的旧路径完全一致；进入底层连接器的搜索调用由248次降为0。该小例只说明减少了重复工作，**不是实际原生仿真或全天加速比**。

46条已核验连接是启动支持，不是完整道路覆盖。当前仍不宣称前瞻已改善接单、C利用率或收益；这些需要下一次明确授权的同一短窗执行结果。
