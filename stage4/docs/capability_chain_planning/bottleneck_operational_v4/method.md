## 为什么改

V3联合组保持约97.5%的服务率，接驾空驶明显减少，但C闲置从83.8%升至87.8%。瓶颈组95个有调位候选的轮次中42轮预算截断，精确计算41,844个调位连接却只启动18次调位。计算开销又主要来自搜索、修复和路由，而不是单个大整数模型。

V4不把闲置率变成奖励，不强制C优先，不放松C能力或乘客条件。目标是恢复有限预算下调位的可执行性，将计算集中到能够改变当前分工的冲突上。

## 1. 调位：先规划少量候选，再认证，最后重算

每15分钟仍为每辆空闲车提出2km内最多3个历史目标，共享最多50辆车的调位上限不变。

1. 保留只包含已验证接单/等待动作的可执行基线。
2. 联合规划可以使用零移动时间、零移动距离的乐观调位提示；此时不调用精确路由，不执行、不保存为物理计划。
3. 只对探测规划实际选中的调位动作查路，最多50条。继续沿用当前的道路、能力、方向、连接、300秒调位时长和班次结束检查。
4. 用精确到达时间、距离和道路上下文重建动作域，再联合求解。未查路及不通过的动作不进入最终动作域。
5. 某条连接失败或预算不足，不清空其他已认证候选；若无法在预算内完成精确重算，则保留原可执行基线，不能执行乐观计划。

整个流程共用原10秒期限。剩余预算的前40%最多用于探测，到70%位置结束新增认证，剩余用于精确重算；不可中断的路由调用仍可能少量越界，必须如实报告。首选连接被拒绝时，只删该候选，在同一探测时间及标签预算内回补其他车辆/站点；精确查路总量仍最多50条，不能无限回补。不增加内存或稀疏模型上限。

这是显式的有限预算启发式，不宣称与全候选精确模型等价。尚未选中的调位候选不会被路由，也不会被错误标成不可行。联合探测不按单车独立收益剪枝，保留中性动作的跨车互补机会。

## 2. C目标：只复用已有历史能力条件需求

C目标使用已经存在的 `operations_v5_input/type_demand_reference.parquet`，数据来自20161010/17/24的历史订单、Stage1起点节点、冻结M3及Stage3能力条件。HV继续使用原全需求目标。常数0.70乘客接受率在归一化空间比例中抵消；不读取Test31未来订单。

历史C目标缺失的时段不主动提出C调位，但不是禁止C接单。目标节点仍在原物理参考网络中，最终可达性仍由精确路由认证。

本轮只改变在线调位目标，不改变C/HV车时、上线/退出时间或47批出生布局。小时供给错配仍可能存在，不能把V4表述成已经完成C供给规模和上线时段优化。

## 3. 搜索：空间基础 + 按需瓶颈扩展

保持3个情景、30分钟规划时域、最多3次未来服务、6车邻域和128个部分状态。

默认按空间邻域联合搜索；当前请求同时存在C/HV选项，或有合法选项但尚未被当前计划覆盖时，使用瓶颈闭合。共享客户容量、跨情景共同首动作和中性联动机制保留。达到第一次严格当前动作改善后停止的规则不变。

没有增加C使用奖励、改变目标层级或声称城市全局最优。目标仍为保护紧急服务，然后比较当前与情景未来总服务、积压服务和空驶。

## 4. 未来计划的精确复用

只缓存已选中、全部来自历史预测的短服务链。同一历史快照内，起点、预测准备时间的300秒网格、班次结束及车型完全相同，且任务仍存在、未被别的车辆占用时，可复用相同代理模型下的腿时间。

实际待接订单、物理道路连接和真实执行时间不复用该捷径。状态、任务冲突或历史快照变化后按原逻辑重新校时。只保留当前选中短链，不累计所有搜索路径。

乐观探测与精确重算使用事务式计划副本；只提交最终可执行结果的计划记忆。同一时刻动作域变化会重新激活搜索，不能被“历史快照未变”误判为无工作。

## 验证范围与停止边界

旧V3配置和结果不覆盖。单独入口：

```powershell
python -B -m stage4.analysis.bottleneck_operational_v4 prepare
python -B -u -m stage4.analysis.bottleneck_operational_v4 prefix --execute
python -B -u -m stage4.analysis.bottleneck_operational_v4 run --execute
```

默认只准备。`prefix`仅检查午夜至00:40的真实原生运行，使用完整日输入与原预测时域，不是完整服务结果，不外推全天精确耗时。`run`只允许一组V4全天确认，参考和旧组不重跑；已有目录拒绝覆盖，无自动重试。

必须区分预期与实测：查询次数有最多50条/调位轮次的结构上限，但是否改善C接单、空驶和全天耗时，要由实际运行回答。不能从小型测试声称C闲置已经降低。
