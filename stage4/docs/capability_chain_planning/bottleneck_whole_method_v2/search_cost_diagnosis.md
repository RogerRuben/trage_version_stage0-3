## 4. 哪些优化有效，为什么总体仍更慢

### 4.1 路径搜索减少，模型评价反而增加

| 联合部分，72个有效决策 | V1 | V2 |
|---|---:|---:|
| 链搜索标签尝试 | 3,590,992 | 1,409,861 |
| 评价的邻域记录 | 4,641 | 7,357 |
| 最大活跃整数模型变量 | 413 | 597 |
| 最大活跃模型非零元 | 1,282 | 1,935 |
| 最大列池 | 2,010 | 3,214 |
| 触及50,000标签上限的轮次 | 71 | 0 |
| 以128个部分状态上限停止的轮次 | 1 | 68 |

V2标签尝试减少60.74%，而邻域评价记录增加58.52%。V1的71轮在50,001次标签探测处停止；额外1次是触发停止的探测。V2没有碰到标签上限，68/72轮则做到了部分状态上限。**优化改变了先碰到哪个预算，却没有把节省的计算转化为更早结束。**

V2实际整数求解19,106次，平均每有效联合决策265.36次；平均一次9.43毫秒。单次非常小，累计数量才是问题。V1没有完整实际调用计数，不能把其推导下界当真实调用数来计算提速；其已保存邻域可推出至少8,965次，但中途阶段也可能有额外调用。

V2不是出现了一个巨大矩阵：最大仍只有597变量、1935非零元。扩大CPU线程或使用GPU不能自动消除每轮数百次独立模型启动、数据转换和状态校验。

### 4.2 缓存是真的，不是没有接入；但缓存层次偏低

已记录：

- 预测快照重建9次、复用63次。
- 后继候选复用42,452次。
- 轮内查询复用402,437次、重复邻域跳过592次。
- 固定根组跳过1,821次，恒零目标阶段跳过1,187次。
- 恢复未来续行18,175次，修补续行4,042次；修补总耗时仅3.96秒。

这些统计足以确认优化实现被实际调用，不能说缓存“完全没用”。但它们优化的是一次查询或一次初始化，**没有抑制上层不断要求新的或近似相同的优化问题**。`actual_query_calls=982,104`是Oracle查询入口次数，含其内部缓存命中，不是982,104次独立深度搜索；也不能和402,437次更外层命中混为同一统计单位。

### 4.3 未来计划一变，整轮邻域访问缓存全部失效

[BlockWorkspace.key](D:/pycodes/didi_xian_raw/.worktrees/stage0-v6-valhalla/stage4/dispatch/bottleneck_incremental.py:150)按整个`JointPlan`对象是否改变来清空邻域访问表。即使只改变一辆远处背景车的未来续行，也会让不相关组的访问标记失效。

这是代码可确认的保守失效机制，不是现有日志已量化的“重复同一个矩阵多少次”。目前没有每次失效的局部依赖足迹，不能声称7,357条邻域记录全是重复模型。但这种整队失效明确解释了为什么已有592次重复跳过仍不足以约束总求解量。

### 4.4 活动前沿会被自己的未来重排和积压再次激活

[frontier](D:/pycodes/didi_xian_raw/.worktrees/stage0-v6-valhalla/stage4/dispatch/bottleneck_incremental.py:73)除了真实新请求和状态变化，还加入上轮未完成种子；[save](D:/pycodes/didi_xian_raw/.worktrees/stage0-v6-valhalla/stage4/dispatch/bottleneck_incremental.py:97)把初始化到最终计划的未来续行变化记录为`touched`，下一轮再扩展相关位置的任务。

因此它不是单纯的外部事件驱动。未来计划改善、尚未做完的搜索，又可以驱动下一轮重新搜索。按既定300秒预测更新频率拆开：

| 有效联合决策 | 300秒更新轮 | 其他30秒细轮 |
|---|---:|---:|
| 决策数 | 8 | 64 |
| 实际整数求解次数 | 1,826 | 17,280 |
| 平均每决策调用 | 228.25 | 270.00 |
| 联合模块时间 | 44.01 s | 376.41 s |
| 平均每决策时间 | 5.50 s | 5.88 s |

90.44%的调用发生在细轮；细轮本来就更多，所以这个比例本身不是浪费证明。真正关键是：**没有更新预测快照的细轮，平均仍比更新轮调用更多模型，并没有退化成轻量修补。**

### 4.5 大部分接受步骤只改未来，但不能简单全部禁止

1,926次局部接受中，1,658次（86.09%）没有改变该次更新的当前根；另外268次更新改变当前根。但72轮中68轮的最终当前动作相对本轮初始见证发生变化，累计240个根变化。

这说明有大量未来计划整理，却**不能**据此认定它们全无价值，或把当前根不变的步骤全部砍掉。中性/纯未来步骤可能是多车互补改善的必要中间过程；禁止它们会破坏原算法设计。正确目标是消除无关重复与无事件再搜索，不是退回只接受单车即时收益。

## 5. 下一步最小而有效的方向——本轮未实施

只需要改共享搜索执行的两件事，不再开一批新条件：

1. **把失效范围缩到真实依赖。** 邻域缓存只依赖本组动作/列版本、相关请求的外部占用、剩余调位容量和紧迫订单保护条件；不因整队任意未来计划变化全部清空。外部占用、相关根或列发生改变仍须重验，不能把旧的未证明访问当成最优证书。未来计划自身改善也不应无条件作为下一轮新的物理事件，未完成种子须区分仍然有影响的真实事件与搜索积压。
2. **同一小车群先合并候选，再一次联合求解。** 现在[evaluate_group](D:/pycodes/didi_xian_raw/.worktrees/stage0-v6-valhalla/stage4/dispatch/bottleneck_incremental.py:212)按种子逐次补列/求解；[populate](D:/pycodes/didi_xian_raw/.worktrees/stage0-v6-valhalla/stage4/dispatch/bottleneck_incremental.py:138)又对组内多个动作、情景和目标交叉查询。应在同一合法依赖状态下合并重叠组的目标与新列，只有可行域或受约束的改进机会真正变化才重新求解，复用已有拥有者/目标增量，减少每次全队扫描。闭合仍允许必要的中性组合，不改成独立车辆价值或加权目标。

两点都保留：共同当前动作、场景共享请求容量、真实待单原期限、外部资源占用、背景忙车续行、最多三单链、最多六车组、原词典序与原物理校验。300秒接单/600秒接驾、10秒决策、内存与稀疏规模上限均不变。

这是有限预算下新的搜索组织，不能事先宣称城市结果严格等价；也没有根据保证某个提速倍数。当前不建议继续把两组全天任务直接挂上去，更不建议把3小时扩大来掩盖问题。先让一次30秒决策不再反复消费相近的整套局部模型，才值得讨论继续比较。
