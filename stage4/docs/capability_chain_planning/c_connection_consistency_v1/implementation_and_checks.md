# C接驾与未来机会的连接一致性：实现与有限检查

## 结论

本轮完成独立开关下的连接层修改，不修改经济目标、C能力或供给，不重跑全天。

当前接驾与未来C链复用同一套有向路线、动作及首尾拼接检查。默认auto接驾路线失败后，可以有限地寻找其他候选；未来搜索只读取已经检查的连接，不在搜索标签循环内查路。

这解决的是“默认路线失败是否被误当成没有C选项”和“未来C机会是否有道路支持”的接口问题。**没有证明C闲置率已经改善，也没有构造完整的C约束最短路算法。**

## 1. 修改范围

### 当前接驾

首先保留默认auto路线。如果它已经通过C道路、动作、snap及出发/到达方向检查，直接使用，不为了追求利用率改路。

如果默认连接失败，在额外预算内最多发起一次替代请求：使用已知上一段的出发航向与客户原路线的进入航向，返回至多三个不同路径候选。航向只能从已有有向边证据产生，缺失时不伪造。每个候选仍经过原来的edge-walk、完整intersection-complex动作解析和连接检查。挑通过者中预计接驾时间最小的路径；客户自己的原路线不变。

这里是有界的候选恢复，并非保证找到所有C可行绕行。默认路径的失败原因被保留；预算耗尽不被记录为已经证明C无法通行。

替代请求使用固定几何快照的invariant时刻（`date_time.type=3`），不依赖机器当前日期。每次使用时仍以预计离开时刻重算原有15分钟接驾系数。Valhalla对时间依赖请求的alternate支持有限，不能把它与固定快照混用。[官方路由API](https://valhalla.github.io/valhalla/api/route/api-reference/)

### 未来C机会

先从已保存的未来链和邻近的历史情景任务中提出小量连接，进行有界预取。后续链搜索只能查缓存，不能启动新的Actor路由。

一个C未来连接必须同时满足：

1. 客户路线仍符合冻结的C研究条件，乘客接受AV。
2. 空车连接及前后两处方向拼接通过同一连接接口。
3. 接单时刻落在原接单期限和车辆接单班次内。
4. 接驾时间不超过独立600秒限制。

下一状态的预计就绪时刻为“该次接单时刻＋已支持连接的预计接驾时间＋冻结M3客户行程时间”。没有读取真实未来行程时间。

注意：300秒是接单期限，不是要求车辆在300秒内到达。共享接口的静态道路证据不缓存某一次的期限判断，使用时重新检查时间。

原V4中用于发现调位候选的乐观探测仍只存在于探测阶段；它明确标记为不可执行。实际调位要先认证，再在真实到达状态下重算，不能把探测用C机会当作最终已认证机会。

### 缓存与边界修正

- 连接支持绑定起终点、已知进入方向、客户来源日期/身份、完整路线身份及固定几何快照，不仅以坐标相同判断。
- 未来链内部的短缓存额外绑定目标来源、位置和M3服务时间，防止不同历史情景的相同合成请求编号串用结果。
- C旧链重新检查支持并重校时，不能使用V4几何代理的精确复用捷径；HV原复用保留。
- 已接但未完成的C车辆使用已知已接客户的末端路线方向。不能把它当成没有进入方向的初始车辆。
- 物理连接使用精确坐标，不拿旧预测位置字符串的7位小数坐标冒充完全相同的位置。
- 共享接驾返回的时间、距离和几何一起进入原生执行，不仅修改匹配分数。

## 2. 效率与内存边界

当前恢复与未来预取共用每轮至多2个额外查询预算槽、每300秒至多32槽。缓存命中也可能占用保守的预取槽，因此槽数不是实际后端调用次数；实际route调用另计。

每轮额外工作累计达到0.15秒后停止追加。**这是停止发起更多工作的阈值，不是单次调用的硬超时。** 一个已经进入的Actor/方向检查不能被中途抢占，仍受外层原10秒决策期限及其安全回退约束。实测单个新连接检查可能接近1秒，不能宣称额外耗时总是低于0.15秒。

预取每次最多查看64个不同连接。几何邻近使用空间树，未构建车辆×订单或全路网稠密矩阵。完整连接缓存继续使用既有32 MiB字节上限；每次搜索内的短结果缓存最多4096项。没有GPU使用，没有重复加载一套完整路网。

未来查询没有检查到的连接，标记为`NOT_EVALUATED`，不宣称物理不可达；它不进入已认证C未来服务数。故本版本的C未来值来自**已支持的稀疏子集**，不是完整网络机会值或无偏估计。预算和预取域可能影响该近似，必须连同未评估计数报告。

HV未来接驾仍使用既有历史速度/几何代理，不能将整个联合规划称为双车型完整道路认证。最终记录分别说明C支持范围与HV代理范围。

## 3. 不改变什么

- Stage1—3产品、M3模型与C/M/A能力条件。
- C客户行程兼容性、5%交通环境预算、乘客接受设定。
- 原客户路线、供给班次、车时、出生布局、种子。
- 300秒接单期限、独立600秒接驾上限、接单后完成承诺。
- 原目标层级：紧急服务保护，然后当前＋预测未来服务、结转、空驶。
- 不强制C优先，不增加“让C忙起来”的奖励，不加入未经确定的运营利润参数。
- 混合Top-K20及原有未来邻域仍保留；本轮不宣称解决了所有候选截断问题。

旧默认仍是`PROXY_V4`。新配置单独启用`BOUNDED_CERTIFIED_C_V1`，不覆盖旧结果，也没有全天启动入口。

## 4. 检查方式与结论边界

保留原有回归，只新增9个集中检查函数，覆盖共享证据、替代路线、缓存/航向区分、跨情景身份、期限、预算、未来链与原生接口。相关测试合计69项通过；compileall及diff check通过。

真实接口检查固定选择8对20161010的历史C兼容订单，按预先规定的身份哈希排序、2 km邻域和时间条件选取，不按查路结果挑选。加载16条客户路线、992个身份token，不读取未来Test31请求，不运行新M3推理或原生仿真。

该检查只回答接口是否可用、是否存在默认路线之外的合法连接、缓存是否真正避免重查。结果见同目录`eight_link_check.json`。它不是C恢复率估计、闲置率改善证明或全日耗时预测。新旧连接检查顺序存在缓存预热，因此不把其单次时间差解释为算法加速。

最终固定快照检查结果：

| 指标 | 结果 |
|---|---:|
| 默认连接通过 | 2 / 8 |
| 有界替代后通过 | 3 / 8 |
| 新增通过连接 | 1（原因为首尾拼接距公共端点过远） |
| 新增连接预计接驾时间 | 515.49秒，满足原600秒上限 |
| 原先通过的连接被丢失 | 0 |
| 8,000次连接缓存查询 | 2.426秒，新增路由0次 |
| 80,000次重复链连接查询 | 1.120秒，只下沉8次证据缓存查询，新增路由0次 |
| 后端route / edge-walk总调用 | 14 / 15（两种不同单位） |
| 全部检查耗时（含准备） | 9.689秒 |
| 检查进程峰值内存 | 456.42 MiB |

这里是相同8对连接的最终实现检查，开发中曾在相同输入上检查接口和计时，不是多个独立样本。原生全天没有执行。已知剩余失败涉及掉头、无信号动作、环岛及一条edge-walk证据问题，不通过改阈值把它们变成正例。单个新连接检查最大约0.784秒，再次说明0.15秒不是可抢占的硬上限。

公开摘要不含订单标识或坐标；原始数据和旧全天产品保持本地不动。

```powershell
python -B -m stage4.analysis.c_connection_consistency probe --execute
```

`prepare`仅生成准备说明；`probe`只执行上述8条历史连接检查。

## 5. 本轮停止点

完成连接层实现与有限验证，不启动新的全天、能力、规模或种子实验。

运营目标暂保留平台服务与空驶权衡。C接驾更远且HV足够时，模型仍可能选择HV；本轮不将这一选择自动判错。若之后研究自有AV收益，需要明确收入、HV支付和AV成本，而不是任意添加C奖励。

真正需要观察的后续变化是：是否新增了原先漏掉的合法C接驾机会、是否去除了没有道路支持的未来机会，以及由此产生的服务/等待/空驶取舍。不能以C多移动、少显示闲置作为单独成功标准。
