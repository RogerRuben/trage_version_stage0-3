## 1. 主线选择与旧场景定位

推荐主线研究：**在相同预定时段供给与相同初始位置支持下，异质服务兼容性及派单策略如何影响服务。**

主环境采用 `COMMON_SESSION_SLOTS + STOP_ADMISSION_FINISH_COMMITTED + COMMON_TRAIN_TOD_REBALANCE`。旧的“HV经验班次、AV全天在线”canonical环境完整保留，解释为全天AV工时替换经验HV班次的运营情景；不将其结果改名为纯能力替代效应，也不覆盖旧文件。

**作者已明确采纳：本研究中上车时间与请求时间近似等价，使用上车时间作为请求释放时间没有问题。** 后续沿用这个设定，不把区分两者、回推下单时刻或增加请求提前量列为必要任务。接驾耐心仍为300秒。冻结接驾时间校准倍率、M3、基于训练期历史订单构造的未来需求、Stage3 C/M/A定义及5%环境外暴露预算均不在本次定义中重选；本次只明确供给、班次和车辆空闲移动。

## 2. 逐小时供给控制：同一套session slots，只改变类型标签

### 2.1 控制对象

复用纯HV参考的8,435个冻结有效service-session模板。每个slot固定：

- `slot_id = source_session_id`，跨场景不改ID；
- 开始接单时刻a_v、停止接单时刻b_v；
- 初始WGS84位置；
- 活动窗口、容量、共同路由支持与物理推进规则。

不删HV窗口去额外加入全天AV。AV是在同一slot上的类型替换，继承该slot的窗口与初始位置；一段班次内不改变类型，也不因profile不适配而删除slot或移到更有利的初始位置。

设预定在线集合为 V_bar(t)={v:a_v≤t<b_v}。所有q_A、C/M/A和派单策略共享相同V_bar(t)，因此总预定在线数量在每一个时刻都相同，比“全天总车时接近”更严格。

对小时h，精确使用窗口重叠秒数：

```text
ell_vh = max(0, min(b_v, (h+1)*3600) - max(a_v, h*3600))
H_base,h = sum_v ell_vh / 3600
H_HV,h + H_AV,h = H_base,h
```

小时统计覆盖日内00:00–24:00；原先60秒订单释放spillover单独保留、单独列出，不静默丢弃。原始a_v、b_v不人为取整到整小时。该控制承诺的是预定接单供给，不是各场景忙碌/空闲车辆数或实际运营车时相同——这些会随派单结果内生变化。

### 2.2 q_A与标签的确定方式

q_A表示日内**预定AV车时占共同预定车时的目标比例**，不是AV车辆数量占比。记录目标q_A以及实际标签集合产生的q_A_realized；旧canonical中的baseline-normalized level另行保留，不混用不同分母。

标签在实验前一次确定：

1. 按slot开始小时×日内窗口时长四分位分层，四分位来自冻结模板，不来自模拟结果。
2. 层内按 `SHA256(COMMON_SLOT|20260824|slot_id)` 排序；时长用精确秒数。
3. 每层选累计车时最接近q_A×该层总车时的前缀；并列取较短前缀。不搜索种子，不根据服务率交换slot。
4. C/M/A与MYOPIC/LOOKAHEAD在同一q_A下共享完全相同的类型标签。不同q_A沿同一层内排序取前缀，AV集合保持嵌套。

q_A=0时全部slot标为HV，q_A=1时全部标为AV。日内权重为0、只涉及spillover的slot不进入日内车时分母，其标签用相同固定哈希的u_v<q_A判定；仍跨profile/算法共享，不能因分母为0而删除其窗口。

离散slot不能保证每小时AV比例恰好等于q_A：输出全部24小时的H_AV,h/H_base,h与误差，不能只报日均比例。**每小时总供给严格相同**与**每小时类型比例近似目标**是两项不同声明。偏差不触发按服务结果调参，也不改为全天AV来凑车时。

这些是effective availability slots，不是8,435辆全天物理车，更不是AV采购数量；不据此计算购车成本或声称复原了真实司机链。若以后研究真实车辆跨班次复用，应作为单独的运营模型，不能在此处悄悄加入。

## 3. 班次退出：b_v停止接新单，不是强制完工时刻

### 3.1 统一接单规则

HV和AV都采用半开窗口：只有a_v≤t<b_v才可接受新订单。仍要求接驾到达≤请求释放+300秒，并满足共同输入/路线支持和对应服务兼容性。

在该主环境中，**不再用 t + pickup_ETA + M3_service_P50 ≤ b_v 拒绝一个新订单**。M3依然预测服务时间、未来再次可用时刻及机会成本，只是不把有误差的预计完工时刻当成推断班次的硬边界。

到b_v时：

| 当前状态 | 动作 |
|---|---|
| 空闲 | 停止接新单，退出候选池 |
| 已承诺接驾/等待上车/载客 | 停止接新单，继续完成该承诺，结束后退出 |
| 未承诺客户的重定位 | 不再接新单；正常完成已开始的物理移动后退出，不瞬移 |

客户承诺从成功分配开始生效，不等到上车才生效；在b_v前接受、b_v后才接到乘客的订单也继续履约。t=b_v不得接受新单。已经退出的slot不能被future graph再次生成可接单机会。

可选的空驶重定位应在启动前要求 `t + empty_ETA ≤ b_v`，避免主动制造尾段加班；这与已承诺客户允许完工后的退出不是同一件事。若后来引入随机实际空驶时长导致超时，仍完成物理移动并记录，不硬编码零overrun。

### 3.2 overtime不是免费资源

分别报告计划在线车时、窗口内接驾/服务/重定位车时、班次后接驾/服务车时、班次后空驶车时。actual operating hours包括班次后仍在执行任务的时段，不把它们伪装成仍可接新单的在线供给；如果后续启用成本，班次后真实工作也要计费。

用真实物理事件时刻记账，而不是用下一次30秒轮询发现完成的时间。跨班次/跨日任务进入原有physical drain；行政运行上限不充当模型中的下班时刻，不取消客户来让程序准时结束。

LOOKAHEAD的未来可用性也按此规则计算：预计完成晚于b_v时不能提供下一次接单机会；但b_v之前已经承诺的当前订单不因此被删除。

## 4. 统一空闲移动：两类车辆共用历史订单分布进行调位

### 4.1 选择的共同规则

之前称“Train-only”，这里具体是**只用训练期的历史订单建立空车调位的需求参考**，不是一种新训练算法。已经统计2016年10月9—24日订单：把每天分为96个15分钟时段，计算每个时段各起点位置的订单比例。共7,211个有坐标的起点；现成参考表和来源记录不重建。

例如，假设历史上08:00—08:15的订单起点有60%位于A、30%位于B、10%位于C，当前有10辆待命车，就先形成A/B/C约6/3/1辆的目标分布，再根据当前车辆位置、可走路线和接驾时间规则决定哪些车值得移动。这是解释用的假设数字，不是本项目实测比例。

只用历史资料确定目标，是为了不提前偷看测试当天尚未出现的真实订单。当前已经出现的请求和当前车辆状态仍可用于正常派单和计算哪些位置缺车。它也不表示只在训练集运行或只服务训练订单。前瞻派单已有的未来需求场景是另一项既有输入，两者本轮不合并训练。

复用已有 `TRAIN_TOD_DEMAND_BALANCE` 的需求目标和确定整数车辆配额的方法，不新增重定位模型，也不读未来真实拥堵。

HV/AV共享同一目标分布、配额公式、目标排序、周期与移动预算。真实客户优先，顺序是：物理到达更新 → 班次接单窗口更新 → 请求/超时更新 → 正常派单 → 剩余空闲车辆重定位。

推荐明确默认值（预先选择的研究规则，非文献统一数值，也未按本轮结果优化）：

| 项目 | 主规则 |
|---|---|
| 正常派单 | 原有30秒rolling |
| 重定位决策 | 15分钟边界，正常派单后 |
| 需求目标 | 冻结Train TOD起点分布，全部车型共用 |
| 可参与车辆 | 尚在接单窗口内、没有客户承诺的空闲车辆 |
| 配额 | 按总待命池计算，不分别给HV/AV做两套配额 |
| 候选目标 | 2km内最近的3个有缺额目标，距离并列按node_id |
| 空驶上限 | 校准route ETA≤300秒且预计在b_v前完成 |
| 每轮成功启动上限 | 全车队共同50次，不按车型分别给50次 |
| 公平排序 | 固定slot哈希/slot_id，不用AV/HV前缀作为优先级 |
| 路由或共同证据不足 | 尝试已列候选；都不满足则原地保持空闲 |

目标配额对空闲与正在执行有效重定位的在线车辆只计一次；已在路上的车辆计向其目标，避免重复填补同一缺额。候选/预算不足留下的缺额如实记录，不把最大余数配额当成已经实现的空间分布。

该上限最多96×50=4,800次新重定位/日；候选只稀疏构造，按小批次处理。不搜索2/3/5km、不同周期或不同预算来选最高服务率。

新重定位仅在日内半开区间[00:00,24:00)的96个边界启动。原有60秒spillover与后续drain只处理客户派单/超时和已有物理任务，不在次日00:00额外启动第97轮重定位。

### 4.2 移动途中可以接真实订单

没有乘客、没有客户承诺的重定位是可中断任务。每30秒正常派单时，在线的这种车辆可从其**真实当前路线位置**成为候选；成功接单才中断旧空驶计划，转去接驾。

没有匹配就继续原目标，不每轮取消/重启移动。已承诺客户的接驾或载客不得被新的空闲移动打断。中断时保留已行驶空驶时间和实际路径前缀距离，不把完整原计划重复记账，不跳回出发点或瞬移到目标。

这要求有可复现的路线几何与中途推进。矩阵只提供ETA/距离，不能据此声称拥有可检查的实际路线；为少量空驶候选调用scalar `route()`，同一次返回的时间、距离、edge序列和polyline作为该次移动的权威记录。不能混用一条matrix路径的时间和另一条route路径的几何。原有大规模接驾稀疏matrix/v4缓存继续保留。

### 4.3 相同策略，不等于抹掉能力约束

空驶也使用同一个Stage3研究兼容性函数：共同路线支持一致，C/M/A的movement与交通状态适配假设不改。C/M不能因为空驶而走其模型禁止的路线；A与HV在共同支持内同等处理。可换目标，但不为失败候选额外开发AV专属重规划算法。

这里明确指当前movement+交通状态的research compatibility，不是退回旧版 `rho_overall≤1` 或旧AV专属hard_state门槛；AMDL、E/Q/C与speed等既有描述保留其预测/解释用途，不重新叠加成硬筛选。

空驶没有乘客，因此不套P_AV乘客接受率。也不追加第二套同源dynamic阈值或“安全分数”。研究状态U沿用既有假设；关键共同路线身份无法解析时两种车型同样不移动，而不是只惩罚AV。

旧实现写明空驶 `OPERATIONAL_ABSTRACTION_NOT_ODD_CERTIFIED`，不能只把AV-only改为both就宣称已满足上述定义。若新路径的Stage3适配接口暂时接不上，明确报告未实现，不静默沿用未判定空驶来运行主实验。本协议仍是科研情景适配，不是自动驾驶安全认证。

## 5. 对现有代码的必要改动（尚未实施）

1. 独立opt-in controlled fleet builder：同slot/窗口/初始位置，仅改类型标签；不覆盖旧 `build_fleet_scenario`。
2. 将接单窗口策略从vehicle_type分支中分离；controlled HV/AV都用stop-admission策略。现有native的“AV必须全时段在线”断言只保留给legacy模式，不能用于新模式。
3. 同步更新零接驾session certificate、正常派单、LOOKAHEAD future graph及physical drain，不能只删除一处完工时间比较。
4. 重定位manager移除AV-only；新增共同配额/类型盲排序、在线时段判定和可中断状态。现有不中途改派不能冒充已支持新规则。
5. 将少量空驶route结果接入现有Stage3解析/兼容逻辑、物理路径推进与中断记账；不用重训M3或重生产Stage0/1。

最低必要检查只有三组：共同供给逐事件/逐小时一致；停止接单、任务完成与overrun账相符；`A=HV、P_AV=1、Gamma关闭、成本系数相同`的标签互换中性检查。后者应保持同slot、同请求、同位置、同规则下的结果等价；不能拿改变了班次窗口的两组来冒充中性检查。

C/M/A和不同算法的实际位置、忙碌时长、可行边与最终服务可以不同，因为它们是模型内生结果；只在固定物理状态下讨论兼容图删边的单调性，不承诺不同完整日轨迹的服务率必然逐场景单调。

## 6. 范围、资源与后续

本轮没有运行命令，没有实验成功率门槛，没有100%目标；本文件不授权新全天运行。未来实现继续沿用v4的CPU-only、小批次、可选512MiB缓存、进程组RSS 2,048MiB上限以及private committed单独报告；不构建订单×车辆或全路网全点对矩阵，也不增加一轮大型审计。

这三项作为一个一致的**主回放环境定义**。若未来比较新旧环境，只能称组合环境变更；若比较派单算法/能力profile，则必须都运行在同一新环境、同一共同订单集和同一类型标签下。原82.40%纯HV与68.58%混合结果仍属于旧环境，不自动成为新环境的配对对照。

后续顺序：实现该独立模式 → 上述最小检查 → 按另行授权运行一个必要环境对照；再推进既定研究比较。不自动扩展日期、q/P列表或参数网格。
